# Протокол оценки качества (EVAL_PROTOCOL)
Этот документ фиксирует, какие метрики считаются и какие результаты считаются “достаточными” для прототипа.

---

## 1) Датасеты и сплиты
- Деление на train/val/test фиксируется seed.
- Для DEAM: split по трекам (не по окнам), чтобы не было утечки.
- Для структуры: split по трекам.

---

## 2) Метрики по эмоциям (DEAM)
Задачи: `arousal_class` (3 класса), `valence_class` (3 класса)

Считать:
- Accuracy
- Macro‑F1
- Confusion matrix

Минимальные ожидания (для прототипа):
- выше случайного (random baseline = ~33% accuracy)
- разумная macro‑F1 (например, >0.40) уже годится как “работает” для НИР
- в отчёте обязателен анализ ошибок (какие классы путаются).

---

## 3) Метрики по структуре (SALAMI/Harmonix/свой набор)
### 3.1 Оценка классификации по окнам
- Window Accuracy
- Macro‑F1 по 4 классам

Это проще всего и честно отражает качество модели как классификатора фрагментов.

### 3.2 Оценка границ сегментов (опционально, но желательно)
Нужно получить boundary‑times из предсказаний.
Метрика:
- Precision/Recall/F1 по границам с допуском `±3 секунды` (или `±1 такт`, если есть бит‑сетка).

Простой алгоритм:
- истинные границы из аннотаций
- предсказанные границы из смены класса после сглаживания
- совпадение, если расстояние <= tolerance

---

## 4) Абляции (минимум 2 эксперимента)
Нужно хотя бы два сравнения:
1) `log-mel` vs `log-mel + chroma` (или mfcc)
2) single-task (только эмоции) vs multi-task (эмоции+структура)

Цель: показать, что выбор архитектуры/признаков обоснован экспериментально.

---

## 5) Качественная оценка
В отчёт вставить 3–5 примеров треков:
- график энергии + предсказанные сегменты
- короткий комментарий: “похоже на куплет/припев”, “дроп выделился” и т.п.

---

## 6) Итоговые критерии “готово”
Проект считается завершённым, если:
- есть обучаемая модель (CNN) + обучение на датасете
- есть инференс, формирующий `timeline.json`
- есть метрики на test (эмоции и/или структура) + анализ ошибок
- есть демонстрация на независимых треках (не из train)
