## 1. Постановка задачи

### 1.1. Цель исследования

Создание системы автоматического анализа музыкальных композиций, способной по входному аудиотреку формировать временную разметку по четырём аспектам одновременно:

1. **Структурная сегментация** — определение типа музыкального фрагмента (Intro, Verse, Bridge, Chorus, Instrumental, Outro) — 6 классов
2. **Arousal (энергия)** — уровень энергетической возбуждённости (Low, Mid, High) — 3 класса
3. **Valence (настроение)** — эмоциональная окраска (Dark, Neutral, Bright) — 3 класса
4. **Genre (жанр)** — музыкальный жанр (blues, classical, country, disco, hiphop, jazz, metal, pop, reggae, rock) — 10 классов

### 1.2. Исследовательские вопросы

- **RQ1**: Насколько эффективна мульти-задачная CNN для одновременного решения четырёх задач?
- **RQ2**: Какой вклад вносит temporal modeling (BiLSTM) по сравнению с per-window классификацией?
- **RQ3**: Какой вклад вносит качество признаков (pretrained PANNs vs from-scratch CNN)?
- **RQ4**: Какой фактор (temporal context или quality of features) оказывает большее влияние?

### 1.3. Почему эти вопросы важны

В области MIR (Music Information Retrieval) каждая из четырёх задач обычно решается отдельной моделью. Мы исследуем возможность **единой мульти-задачной модели**, что имеет практическое значение: один inference-проход вместо четырёх, общие представления для связанных задач, меньшее потребление ресурсов.

## 2. Данные

### 2.1. DEAM (Database for Emotional Analysis in Music)

- **Объём**: 1802 трека, 45-секундные фрагменты
- **Аннотации**: непрерывные значения arousal и valence (1–9) по времени
- **Квантизация**: разбиение на 3 класса по порогам 33-й и 66-й перцентилей
- **Разбиение**: 70% train / 15% val / 15% test (стратифицированное)
- **Почему DEAM**: крупнейший публично доступный датасет музыкальных эмоций с временными аннотациями

### 2.2. Harmonix Set (структурная сегментация)

- **Объём**: 912 треков (746 с доступным аудио), полноформатные композиции
- **Аннотации**: посекундные метки типа сегмента (Intro, Verse, Bridge, Chorus, Instrumental, Outro)
- **Аудио**: загружено с YouTube через yt-dlp (конвертация в WAV 22050 Hz)
- **Проблема**: 166 треков недоступны (удалены с YouTube) — потеря ~18% данных
- **Разбиение**: 70/15/15 по трекам
- **Почему Harmonix**: единственный крупный публичный датасет структурной сегментации с точными временными границами

### 2.3. GTZAN (жанровая классификация)

- **Объём**: 999 треков по 30 секунд (файл fault.wav исключён), 10 жанров по ~100 треков
- **Разбиение**: 70/15/15 стратифицированное
- **Почему GTZAN**: де-факто стандартный бенчмарк для жанровой классификации, несмотря на известные недостатки (повторы, ошибки разметки). Используется для сопоставимости с литературой

### 2.4. Предобработка аудио

Для всех датасетов применяется единый пайплайн:

1. Загрузка аудио: mono, sr=22050 Hz (librosa)
2. Извлечение log-mel спектрограммы: n_mels=128, n_fft=2048, hop_length=512, fmin=30 Hz
3. Оконное разбиение: window_seconds=10.0, hop_seconds=1.0
4. Каждое окно: тензор размерности (1, 128, W), где W = 10.0 * 22050 / 512 ≈ 431 фрейм

**Почему 10 секунд**: изначально использовали 8 секунд. Увеличение до 10 секунд даёт модели больше контекста для определения структуры (типичный музыкальный фрагмент — 8-16 секунд). При этом не увеличивает потребление GPU памяти значительно.

## 3. Архитектура модели

### 3.1. Общая схема

```
Audio (WAV) → Log-Mel Spectrogram → [Window 10s] → CNN Backbone → Task Heads
                                                                  ├─ Segment (6 cls)
                                                                  ├─ Arousal (3 cls + reg)
                                                                  ├─ Valence (3 cls + reg)
                                                                  └─ Genre (10 cls)
```

### 3.2. CNN Backbone (v2, финальная версия)

Архитектура — 5 свёрточных блоков с SE-attention:

| Блок | Каналы | Операции |
|------|--------|----------|
| Conv1 | 1 → 32 | Conv2D(3×3) → BN → ReLU → SE(32) → MaxPool(2×2) |
| Conv2 | 32 → 64 | Conv2D(3×3) → BN → ReLU → SE(64) → MaxPool(2×2) |
| Conv3 | 64 → 128 | Conv2D(3×3) → BN → ReLU → SE(128) → MaxPool(2×2) |
| Conv4 | 128 → 256 | Conv2D(3×3) → BN → ReLU → SE(256) → MaxPool(2×2) |
| Conv5 | 256 → 512 | Conv2D(3×3) → BN → ReLU → SE(512) → MaxPool(2×2) |
| GAP | 512 → 512 | AdaptiveAvgPool2d(1) |
| Shared FC | 512 → 256 | Linear → BN → ReLU → Dropout(0.4) |
| Heads | 256 → N | Linear(256 → N_classes) per task |

**Общее количество параметров**: ~800K

**Почему SE-блоки (Squeeze-and-Excitation)**: SE-блоки выполняют канальное внимание — модель обучается автоматически взвешивать важность каждого частотного фильтра. Для аудио это особенно полезно: разные частотные диапазоны несут разную информацию для разных задач (низкие частоты важнее для жанра, средние — для мелодии и структуры).

**Почему 5 блоков вместо 4**: начальная версия имела 4 блока и 256 каналов на выходе (~400K параметров). Диагностика показала, что модель underfitting на segment task — ёмкости не хватало для одновременного решения 4 задач. Добавление 5-го блока увеличило ёмкость до ~800K без чрезмерного роста (для сравнения: ResNet-18 ~11M, PANNs CNN14 ~80M).

**Почему Shared FC**: промежуточный полносвязный слой (512→256) с BN и Dropout выполняет роль "бутылочного горлышка", заставляя модель формировать компактное общее представление перед task-specific головами. Это снижает переобучение отдельных голов.

### 3.3. Эволюция архитектуры (v1 → v2)

| Параметр | v1 | v2 | Причина изменения |
|----------|----|----|-------------------|
| Conv блоков | 4 | 5 | Недостаточная ёмкость для 4 задач |
| Выход GAP | 256 | 512 | Больше каналов в последнем блоке |
| Shared FC | нет | 512→256 | Снижение переобучения голов |
| Параметры | ~400K | ~800K | Увеличение ёмкости |
| Window | 8.0s | 10.0s | Больше контекста для segment |

### 3.4. BiLSTM-конфигурации

Для конфигов 2 и 4 поверх backbone-embeddings добавляется BiLSTM:

**CNN+BiLSTM (конфиг 2):**
- Вход: CNN embeddings (512-dim) per window
- BiLSTM: input=512, hidden=128, layers=2, bidirectional → output=256
- Projection: нет (уже 256)
- Heads: Linear(256 → N)
- Параметры: ~928K

**PANNs+BiLSTM (конфиг 4):**
- Вход: PANNs CNN14 embeddings (2048-dim) per window
- Projection: Linear(2048 → 512)
- BiLSTM: input=512, hidden=256, layers=2, bidirectional → output=512
- Heads: Linear(512 → N)
- Параметры: ~2.4M

**Почему BiLSTM, а не Transformer**: при длине последовательности ~30-200 окон на трек BiLSTM эффективнее Transformer (O(n) vs O(n²)). Кроме того, BiLSTM лучше справляется с маленькими датасетами благодаря индуктивному bias'у к последовательной обработке.

## 4. Обучение

### 4.1. Мульти-задачный тренировочный цикл

Три датасета объединяются через **RoundRobinLoader**: на каждой итерации берётся один батч из DEAM, один из Structure, один из GTZAN. Это гарантирует, что ни один датасет не доминирует в обучении.

Функция потерь — взвешенная сумма:

```
L_total = 1.5 * L_segment + 1.0 * L_arousal_cls + 1.0 * L_valence_cls
        + 0.5 * L_arousal_reg + 0.5 * L_valence_reg + 1.0 * L_genre
```

**Почему segment weight = 1.5**: сегментация — самая сложная задача (6 классов, сильный дисбаланс). Без повышенного веса модель "ленится" учить segment, фокусируясь на более лёгких задачах (genre, arousal).

### 4.2. Функция потерь: Focal Loss

Вместо стандартного CrossEntropy используется **Focal Loss** с gamma=1.5:

```
FL(p) = -α * (1-p)^γ * log(p)
```

**Почему Focal Loss**: датасет структурной сегментации крайне несбалансирован:
- Verse ~35% всех окон
- Chorus ~25%
- Bridge ~10%
- Intro ~10%
- Instrumental ~10%
- Outro ~10%

Focal Loss снижает вклад "лёгких" примеров (мажоритарных классов), заставляя модель фокусироваться на трудных примерах (редких классов).

**Почему gamma=1.5, а не 2.0**: изначально gamma=2.0 слишком агрессивно подавляла лёгкие примеры. При gamma=2.0 в сочетании с class weights=4.0 модель чрезмерно фокусировалась на редких классах (Intro recall=64%, но Verse recall=10%). Снижение до 1.5 выровняло баланс.

### 4.3. Взвешивание классов

Inverse-frequency weighting с ограничением max_class_weight=2.5:

```python
weights[c] = min(max_weight, N_total / (N_classes * N_c))
```

**Почему max_class_weight=2.5, а не 4.0**: это была ключевая диагностика. При max_class_weight=4.0:
- Intro recall = 64.2%, precision = 28.9% (завышенный recall, низкая precision)
- Verse recall = 10.1%, precision = 68.9% (модель почти не предсказывала Verse)
- Chorus recall = 18.4%, precision = 70.9% (аналогично)

Модель переоценивала редкие классы. Снижение до 2.5 дало:
- Intro recall = 59.8%, precision = 34.1% (небольшое снижение recall, рост precision)
- Verse recall = 27.9%, precision = 52.1% (значительный рост recall)
- Chorus recall = 40.3%, precision = 53.5% (значительный рост recall)

### 4.4. Оптимизатор и планировщик

- **Оптимизатор**: AdamW (lr=1e-3, weight_decay=5e-4)
- **Планировщик v1**: OneCycleLR (max_lr=1e-3, warmup 30%)
- **Планировщик v2 (CNN baseline)**: CosineAnnealingWarmRestarts (T_0=10, T_mult=2, eta_min=1e-6)

**Почему CosineAnnealingWarmRestarts**: при 50 эпохах OneCycleLR слишком быстро уменьшает LR. CosineWarmRestarts даёт модели "вторые шансы" — после каждого перезапуска LR возвращается к высокому значению, что позволяет выйти из локальных минимумов. Схема перезапусков: эпохи 0-10, 10-30, 30-90 (экспоненциальное увеличение периода).

### 4.5. Аугментация

1. **SpecAugment**: маскирование случайных полос по частоте (freq_mask=27 бинов) и по времени (time_mask=60 фреймов), n_masks=2. Применяется только при обучении. Предотвращает переобучение на конкретные частотные паттерны.

2. **Mixup** (alpha=0.2): линейная интерполяция пар примеров и их меток. Сглаживает решающую границу, снижает переобучение. Применяется только для per-window конфигов (не для BiLSTM, т.к. смешивание последовательностей нарушает temporal structure).

3. **Temporal Jitter** (±1.0s): случайный сдвиг начала окна при обучении. Предотвращает запоминание точных временных позиций.

### 4.6. Early Stopping

patience=15 эпох по val_loss. Сохраняются два чекпоинта:
- `best.pt` — модель с наименьшим val_loss
- `last.pt` — модель после последней эпохи

**Важное наблюдение**: для segment task `last.pt` оказался лучше `best.pt` (35.3% vs 30.5%). Причина: val_loss является суммой всех задач, и early stopping оптимизирует общий loss, а не отдельную задачу. Segment loss продолжал улучшаться после того, как arousal/valence loss начали расти. Это говорит о **конфликте задач** — улучшение segment происходит за счёт emotion tasks.

## 5. Результаты факторного эксперимента

### 5.1. Первый запуск (v1): 30 эпох, OneCycleLR

| Конфиг | Segment acc/F1 | Arousal acc/F1 | Valence acc/F1 | Genre acc/F1 |
|--------|----------------|----------------|----------------|--------------|
| CNN per-window | 24.3 / 23.1 | **65.9 / 65.3** | **55.8 / 53.4** | **82.7 / 81.9** |
| CNN+BiLSTM | 25.9 / 26.8 | 53.0 / 51.8 | 49.5 / 48.4 | 45.5 / 42.5 |
| PANNs per-window | 23.2 / 20.5 | 60.9 / 61.4 | 54.3 / 52.7 | 81.6 / 81.2 |
| PANNs+BiLSTM | **31.4 / 31.5** | 62.8 / 62.9 | 55.9 / 56.0 | 81.0 / 80.5 |

**Диагностика проблем v1:**

1. **Segment 24%**: per-class анализ показал катастрофический дисбаланс — Verse recall=10%, Chorus recall=18%. Модель перепредсказывала редкие классы (Intro, Instrumental) из-за слишком агрессивных class weights (max=4.0).

2. **CNN+BiLSTM провалился на genre (45%)**: переобучение на маленьком train set. GTZAN содержит всего ~700 train треков, при обучении BiLSTM каждый трек — одна последовательность. По 70 train примеров на жанр — недостаточно для двухслойного BiLSTM.

3. **PANNs не превзошёл CNN**: вопреки ожиданиям, pretrained PANNs CNN14 embeddings не дали значительного преимущества. Возможная причина — domain mismatch: PANNs обучался на AudioSet (звуки окружающей среды, речь, музыка), а не специфически на музыке. Для жанра и эмоций музыкально-специфичные features нашего CNN оказались не хуже.

4. **BiLSTM помог segment (+7% для PANNs)**: temporal context важен для структурной сегментации — тип сегмента зависит от контекста (где мы в песне).

### 5.2. Второй запуск (v2): улучшенная модель, 50 эпох

Применённые улучшения:

- focal_gamma: 2.0→1.5
- window_seconds: 8.0→10.0
- segment loss weight: 1.0→1.5
- CosineAnnealingWarmRestarts для CNN baseline
- Temporal jitter ±1.0s
- CNN embeddings пересчитаны: 256→512 dim

4. **PANNs конфиги почти не изменились**: улучшения backbone не затронули PANNs (frozen pretrained). Небольшие изменения от focal_gamma и class weights.

## 6. Анализ факторов (ответы на RQ)

### 6.1. RQ1: Эффективность мульти-задачной CNN

Мульти-задачная CNN эффективна для genre (84%) и arousal (62-65%), умеренно эффективна для valence (52-55%), и ограниченно эффективна для segment (35%). Основное ограничение — **конфликт задач**: улучшение segment снижает emotion metrics и наоборот. Это подтверждается экспериментом с segment weight (1.0→1.5): segment улучшился на +11%, но arousal просел на -4%.

### 6.2. RQ2: Вклад temporal modeling (BiLSTM)

Эффект BiLSTM — **задачезависимый**:

| Сравнение | Segment | Arousal | Valence | Genre |
|-----------|---------|---------|---------|-------|
| CNN+LSTM vs CNN (v2) | -3.1 | +0.3 | +2.5 | -23.0 |
| PANNs+LSTM vs PANNs (v2) | +8.9 | +3.7 | +1.2 | -4.2 |
| Среднее влияние | +2.9 | +2.0 | +1.9 | **-13.6** |

BiLSTM **помогает segment** (особенно с PANNs: +8.9%), **немного помогает emotion** (+2-4%), но **вредит genre** (-4 до -23%). Причина падения genre: BiLSTM обрабатывает целые треки как последовательности, а GTZAN содержит мало треков (~70 на жанр в train). BiLSTM переобучается на таком малом количестве последовательностей.

### 6.3. RQ3: Вклад pretrained features (PANNs)

| Сравнение | Segment | Arousal | Valence | Genre |
|-----------|---------|---------|---------|-------|
| PANNs vs CNN (v2) | -11.3 | -0.8 | +2.1 | -2.0 |
| PANNs+LSTM vs CNN+LSTM (v2) | +0.7 | +2.6 | +0.8 | +16.8 |
| Среднее влияние | -5.3 | +0.9 | +1.5 | +7.4 |

PANNs **помогает genre** в BiLSTM-конфиге (+16.8% — компенсирует нехватку данных для BiLSTM), **слегка помогает emotion** (+1-3%), но **не помогает segment** (даже ухудшает для per-window). Наш CNN, обученный на музыкальных задачах, формирует более релевантные для segment features, чем PANNs, обученный на AudioSet.

### 6.4. RQ4: Что важнее — temporal context или quality of features?

**Для segment**: temporal context важнее (BiLSTM даёт +2.9%, PANNs даёт -5.3%). Тип сегмента зависит от позиции в песне.

**Для emotion**: оба фактора слабо влияют (+2.0% и +0.9%). Эмоции определяются скорее локальными акустическими характеристиками.

**Для genre**: quality of features важнее (PANNs +7.4%, BiLSTM -13.6%). Жанр — глобальное свойство трека, BiLSTM не добавляет полезной информации, а PANNs приносит обобщённые аудио-features.

**Общий вывод**: ни один фактор не доминирует — оптимальная конфигурация **зависит от задачи**. Для практического применения рекомендуется **ensemble** из CNN per-window (для genre/segment) и PANNs+BiLSTM (для emotion).

## 7. Технические сложности и решения

### 7.1. Загрузка аудио Harmonix Set

**Проблема**: аудио Harmonix Set не распространяется напрямую — только YouTube ID. Из 912 треков 166 удалены с YouTube.

**Решение**: скрипт `scripts/download_harmonix_audio.py` с yt-dlp. При первом запуске все 912 загрузок провалились — ffmpeg отсутствовал в venv. Установка `imageio-ffmpeg` в venv решила проблему. Успешно загружено 746/912 треков.

### 7.2. Проблема с class weights

**Проблема**: max_class_weight=4.0 приводил к парадоксу — редкие классы (Intro, Instrumental) имели высокий recall, но низкую precision, а мажоритарные (Verse, Chorus) — высокую precision, но recall <20%.

**Диагностика**: per-class анализ eval_cnn.csv показал, что модель overpredict'ила редкие классы. Loss для мажоритарных классов был занижен из-за Focal Loss * low class weight, и модель "забывала" их предсказывать.

**Решение**: снижение max_class_weight до 2.5 и focal_gamma до 1.5. Это перераспределило внимание модели: Verse recall вырос с 10% до 28%, Chorus — с 18% до 40%.

### 7.3. Early stopping vs best checkpoint

**Проблема**: best.pt (по val_loss) давал segment=30.5%, а last.pt — segment=35.3%. Early stopping оптимизировал общий loss, который переставал улучшаться из-за arousal/valence overfitting, хотя segment ещё учился.

**Решение**: для CNN baseline использован last.pt. В будущем стоит использовать task-specific early stopping или Pareto-optimal checkpoint selection.

### 7.4. Несовместимость размерности embeddings

**Проблема**: после обновления CNN с 4 до 5 блоков embeddings изменились с 256-dim на 512-dim. Старые embedding файлы (256-dim) остались на диске. Скрипт precompute_embeddings.py пропускал существующие файлы (skip if exists).

**Решение**: удаление старых .npy файлов и пересчёт всех embeddings с обновлённым чекпоинтом.

## 9. Выводы и перспективы

### 9.1. Что достигнуто

1. Построена работающая мульти-задачная система анализа музыки (4 задачи, 3 датасета)
2. Проведён 2×2 факторный эксперимент с 4 конфигурациями в двух итерациях (v1, v2)
3. Показано улучшение segment classification на +11% через диагностику и тюнинг
4. Получены конкурентные результаты по genre (84%) на стандартном бенчмарке
5. Дан ответ на исследовательские вопросы: оптимальная конфигурация зависит от задачи

### 9.2. Ограничения текущего подхода

1. **Segment 35%** — ниже SOTA (~65-70% для специализированных моделей)
2. **Valence 55%** — на грани случайного
3. **Конфликт задач** — улучшение одной задачи ухудшает другие
4. **CNN backbone слабый** — ~800K параметров vs 85M+ у современных моделей (AST, HTS-AT)

### 9.3. Направления улучшения

1. **Замена backbone на AST (Audio Spectrogram Transformer)** — pretrained на AudioSet, 768-dim embeddings. Ожидаемый прирост: segment 45-55%, genre 92-95%.
2. **Ensemble** нескольких конфигов — бесплатный прирост +2-3%
3. **Task-specific early stopping** — решение проблемы конфликта задач
4. **Boundary detection** — замена classification подхода на boundary detection для segment (предсказание границ сегментов вместо типов окон)
