# Подробный отчёт по экспериментальной части НИР

> **Тема**: Модуль анализа музыкальных композиций на основе мульти-задачного глубокого обучения
> **Университет**: ТвГУ, магистратура
> **Проект**: musicml-timeline

---

## 1. Постановка задачи

### 1.1 Цель исследования

Создание прототипа системы автоматического анализа музыкальных композиций, способной по входному аудиотреку формировать **временную разметку** (timeline) с четырьмя аспектами:

1. **Структурная сегментация** — определение типа сегмента (Intro, Verse, Bridge, Chorus, Instrumental, Outro)
2. **Arousal** (уровень энергии) — Low / Mid / High
3. **Valence** (эмоциональная окраска) — Dark / Neutral / Bright
4. **Genre** (жанр) — 10 классов (blues, classical, country, disco, hiphop, jazz, metal, pop, reggae, rock)

### 1.2 Исследовательские вопросы

- **RQ1**: Насколько эффективна мульти-задачная CNN для одновременного решения четырёх задач анализа музыки?
- **RQ2**: Какой вклад вносит temporal modeling (BiLSTM) по сравнению с per-window классификацией?
- **RQ3**: Какой вклад вносит качество признаков (pretrained PANNs vs from-scratch CNN)?
- **RQ4**: Какой фактор — temporal context или quality of features — оказывает большее влияние?

### 1.3 Обоснование мульти-задачного подхода

Четыре задачи анализа музыки тесно связаны между собой: жанр определяет типичную структуру (рок — verse-chorus, классика — более свободная форма), эмоциональная динамика коррелирует со структурными переходами (chorus обычно ярче verse). **Мульти-задачное обучение** позволяет модели использовать эти корреляции: общий backbone извлекает универсальные аудиопризнаки, а специализированные головы адаптируют их под каждую задачу. Это также выступает формой регуляризации — модель обучается более робастным представлениям, поскольку они должны быть полезны для нескольких задач одновременно.

## 2. Данные

### 2.1 Используемые датасеты

| Датасет | Размер | Задача | Источник |
|---------|--------|--------|----------|
| **DEAM** | 1802 трека | Arousal, Valence | MediaEval 2013–2018, crowdsourced аннотации |
| **Harmonix Set** | 912 треков (746 с аудио) | Segment | Nieto et al. 2019, профессиональные аннотации |
| **GTZAN** | 999 треков | Genre | Tzanetakis & Cook 2002, 10 жанров × ~100 треков |

### 2.2 Обоснование выбора датасетов

**DEAM** выбран как крупнейший открытый датасет для emotion recognition в музыке. Содержит непрерывные аннотации arousal и valence по шкале Russell's circumplex model. Мы квантизовали непрерывные значения в 3 класса (Low/Mid/High для arousal, Dark/Neutral/Bright для valence), поскольку:
- Непрерывные аннотации имеют высокую субъективную вариативность между аннотаторами (inter-annotator agreement ρ ≈ 0.5–0.6)
- Для задачи временной разметки (timeline) дискретные категории информативнее, чем числа
- 3 класса — минимальная гранулярность, сохраняющая семантику (низкий/средний/высокий)

**Harmonix Set** — единственный крупный открытый датасет со структурной разметкой реальных треков (не синтетических). Аннотации выполнены профессиональными музыкантами, включают 6 типов сегментов. Проблема: аудио не распространяется напрямую, необходимо скачивание через YouTube (yt-dlp). Из 912 треков удалось получить аудио для 746 (81.8%), остальные удалены с YouTube.

**GTZAN** — де-факто стандартный бенчмарк для genre classification с 2002 года. Несмотря на известные ограничения (дупликаты, ошибки маркировки), он остаётся наиболее широко используемым, что обеспечивает сравнимость результатов с литературой. SOTA на GTZAN: ~95% (pretrained трансформеры), типичные CNN результаты: 75–85%.

### 2.3 Предобработка данных

**Feature extraction:**
- **Log-mel спектрограмма** (128 bins, sr=22050, hop_length=512, n_fft=2048) — основной признак. Выбрана как стандарт de facto для аудио-CNN. 128 мел-полос покрывают диапазон 30–11025 Hz, достаточный для анализа музыки.
- Windowing: трек нарезается на окна по `window_seconds` с шагом `hop_seconds=1.0s`. Каждое окно — один вход в модель.
- **Нормализация**: global mean/std по train split, вычисляется при подготовке данных и применяется к train/val/test.

**Разбиение данных:**
- 70% train / 15% validation / 15% test для каждого датасета
- Seed=42 для воспроизводимости
- Разбиение на уровне треков (не окон), чтобы окна одного трека не попали в разные split'ы

### 2.4 Дисбаланс классов

Ключевая проблема — сильный дисбаланс в segment classification:

| Класс | Доля в данных |
|-------|--------------|
| Verse | ~35% |
| Chorus | ~25% |
| Bridge | ~12% |
| Intro | ~10% |
| Instrumental | ~10% |
| Outro | ~8% |

Verse и Chorus составляют ~60% данных. Без специальной обработки модель просто предсказывает мажоритарные классы. Это центральная проблема, которую мы решали на протяжении всего исследования.

## 3. Архитектура модели

### 3.1 CNN Backbone

**Финальная архитектура (v2):**

```
Input: (B, 1, 128, T) — batch × channels × mel_bins × time_frames

Conv Block 1: Conv2D(1→32, 3×3) → BN → ReLU → SE(32) → MaxPool(2×2)
Conv Block 2: Conv2D(32→64, 3×3) → BN → ReLU → SE(64) → MaxPool(2×2)
Conv Block 3: Conv2D(64→128, 3×3) → BN → ReLU → SE(128) → MaxPool(2×2)
Conv Block 4: Conv2D(128→256, 3×3) → BN → ReLU → SE(256) → MaxPool(2×2)
Conv Block 5: Conv2D(256→512, 3×3) → BN → ReLU → SE(512) → MaxPool(2×2)

Global Average Pooling → (B, 512)
Shared FC: Linear(512→256) → BN → ReLU → Dropout(0.4)

Head (segment):   Linear(256→6)
Head (arousal):   Linear(256→3)
Head (valence):   Linear(256→3)
Head (genre):     Linear(256→10)
```

**~800K параметров** (backbone ~750K, heads ~50K суммарно).

### 3.2 Обоснование архитектурных решений

#### Почему 5 conv-блоков (а не 4 или 6)?

В v1 использовалось 4 блока (32→64→128→256), что давало 256-dim embedding после GAP. При анализе результатов v1 мы выявили, что модель недостаточно мощна для четырёх задач одновременно — segment accuracy всего 24%. Добавление 5-го блока (→512) удваивает размерность представления, даёт модели больше ёмкости для кодирования разнородных признаков. 6 блоков не добавили — при 5 блоках MaxPool(2×2) уже сильно уменьшает spatial dimensions (128→4 по частоте), дальнейший pooling привёл бы к потере информации.

#### Почему SE-блоки (Squeeze-and-Excitation)?

SE-блок (Hu et al., 2018) позволяет модели адаптивно перевзвешивать каналы:

```
Global Avg Pool → FC(C, C//16) → ReLU → FC(C//16, C) → Sigmoid → Channel-wise multiply
```

Для мульти-задачного обучения это особенно ценно: разные каналы CNN содержат разные типы признаков (ритмические, гармонические, тембровые), и SE позволяет каждому слою "выбирать" наиболее информативные каналы. SE добавляет минимальное количество параметров (~2% от общего числа) при заметном улучшении представлений.

#### Почему Shared FC перед головами?

В v1 головы подключались напрямую к GAP(256). В v2 добавлен промежуточный слой:
```
Linear(512→256) → BN → ReLU → Dropout(0.4)
```

Причина: 512-dim embedding из GAP содержит "сырые" spatial features. Shared FC выступает как "адаптер" — проецирует 512-dim в более компактное 256-dim пространство, в котором представления структурированы для classification. BatchNorm стабилизирует распределение, Dropout регуляризует. Головам проще работать с этим 256-dim представлением.

#### Почему BiLSTM, а не Transformer?

BiLSTM выбран для temporal modeling по следующим причинам:

1. **Размер данных**: наши тренировочные наборы малы (522 трека structure, 1261 DEAM, 699 GTZAN). Трансформеры требуют значительно больше данных для обучения self-attention — при наших объёмах BiLSTM более стабилен.

2. **Длина последовательности**: типичный трек длится 3–5 минут, что при hop=1s даёт ~180–300 окон. BiLSTM эффективно работает с такими последовательностями. Трансформер с квадратичной сложностью O(n²) был бы избыточен.

3. **Количество параметров**: BiLSTM(hidden=128, layers=2) добавляет ~400K параметров. Transformer с comparable performance потребовал бы ~2–5M параметров и больший batch size.

4. **Bidirectional**: музыкальная структура симметрична — знание о том, что дальше идёт Chorus, помогает классифицировать текущее окно как Verse (и наоборот). BiLSTM естественно моделирует это через forward и backward pass.

### 3.3 Конфигурации 2×2 эксперимента

| | Per-window | Sequence (BiLSTM) |
|---|---|---|
| **From-scratch CNN** | **Конфиг 1**: CNN backbone → heads | **Конфиг 2**: CNN embeddings (512d) → BiLSTM(128) → heads |
| **Pretrained PANNs** | **Конфиг 3**: PANNs CNN14 (2048d) → linear heads | **Конфиг 4**: PANNs (2048d) → proj(512) → BiLSTM(256) → heads |

**PANNs CNN14** (Kong et al., 2020) — CNN, предобученная на AudioSet (2M аудиозаписей, 527 звуковых классов). Выдаёт 2048-dim embeddings. Используем frozen (без fine-tuning), поскольку:
- Fine-tuning 80M параметров на наших малых данных приведёт к переобучению
- Frozen embeddings позволяют precompute — значительное ускорение обучения

## 4. Обучение

### 4.1 Функция потерь: Focal Loss

**Выбор**: Focal Loss (Lin et al., 2017) вместо стандартного CrossEntropy.

**Обоснование**: при сильном дисбалансе классов (Verse 35% vs Outro 8%) стандартный CE переоптимизируется на мажоритарные классы. Focal Loss добавляет модулирующий фактор:

```
FL(p) = -α(1 - p)^γ · log(p)
```

Параметр γ снижает вклад "лёгких" (хорошо классифицированных) примеров, заставляя модель фокусироваться на "трудных". Это особенно важно для segment classification, где миноритарные классы (Outro, Instrumental) критически важны для полноценного timeline.

### 4.2 Гиперпараметры и их эволюция

#### gamma: 2.0 → 1.5

**v1 (gamma=2.0)**: слишком агрессивное подавление "лёгких" примеров. Модель фокусировалась почти исключительно на трудных миноритарных классах, жертвуя accuracy на мажоритарных. Результат: Instrumental recall=62.5%, но Verse recall=10%.

**v2 (gamma=1.5)**: более мягкий баланс. Модель всё ещё уделяет внимание трудным примерам, но не игнорирует мажоритарные классы. Результат: Verse recall вырос с 10% до 28%, Chorus с 18% до 40%, при этом Instrumental recall снизился с 62.5% до 29.4%.

**Обоснование значения 1.5**: литература рекомендует γ ∈ [1.0, 2.0] для задач с умеренным дисбалансом. При 6 классах с соотношением 4:1 (Verse:Outro) дисбаланс умеренный, поэтому γ=1.5 — компромисс.

#### max_class_weight: 4.0 → 2.5

Class weights в Focal Loss вычисляются как inverse frequency (обратная частота класса) и обрезаются по max_class_weight.

**v1 (max=4.0)**: вес Outro/Instrumental в 4 раза больше веса Verse. Это слишком агрессивно — модель переобучалась на миноритарных классах, предсказывая Intro/Instrumental там, где должен быть Verse. Precision миноритарных классов была низкой (~10–19%).

**v2 (max=2.5)**: более консервативная коррекция. Verse recall вырос 10→28%, Chorus 18→40%, при этом Intro precision улучшился с 28.9% до 34.1%.

**Обоснование**: max_weight ≈ ratio(max_class / min_class) — эмпирическое правило. Наш ratio ~4:1, но полная компенсация (4.0) оказалась чрезмерной. Частичная компенсация (2.5 ≈ sqrt(4)) работает лучше.

#### window_seconds: 8.0 → 10.0

**v1 (8s)**: 8-секундное окно захватывает ~2–4 такта при типичном темпе 120 BPM. Это достаточно для genre и emotion, но может быть мало для структурной сегментации — музыкальная фраза обычно длится 4–8 тактов (8–16 секунд).

**v2 (10s)**: больше контекста для segment classification. 10 секунд ≈ 4–5 тактов, что лучше захватывает структурные паттерны (повторяющиеся аккордовые последовательности, мелодические мотивы).

**Trade-off**: увеличение окна снижает temporal resolution (граница между сегментами определяется менее точно), но улучшает quality of classification.

#### segment loss weight: 1.0 → 1.5

В мульти-задачном обучении потери от разных задач суммируются с весами:
```
L_total = w_seg * L_segment + w_aro * L_arousal + w_val * L_valence + w_genre * L_genre
```

**v1**: все веса = 1.0. Результат: genre и emotion доминировали в обучении (их loss быстрее уменьшался), а segment "отставал".

**v2 (w_seg=1.5)**: приоритизация segment classification. Обоснование: segment — самая сложная задача (6 несбалансированных классов), и ей требуется больший вклад в градиенты backbone.

#### epochs: 30 → 50, patience: 10 → 15

**v1**: 30 эпох с patience=10 — модель часто не успевала сходиться, особенно на segment. OneCycleLR жёстко привязан к 30 эпохам.

**v2**: 50 эпох с patience=15 — больше времени на обучение. CosineAnnealingWarmRestarts (для CNN baseline) периодически "перезапускает" learning rate, что позволяет модели выбираться из локальных минимумов.

### 4.3 Оптимизатор: AdamW

**Выбор**: AdamW (Loshchilov & Hutter, 2019) вместо Adam или SGD.

- SGD отвергнут: требует тщательного подбора learning rate и momentum, чувствителен к batch size. При multi-task обучении с RoundRobinLoader (чередование батчей из разных задач) SGD нестабилен.
- Adam отвергнут: weight decay в Adam реализован неправильно (L2 regularization вместо настоящего weight decay).
- AdamW: decoupled weight decay, работает стабильно с разными learning rates и задачами.

**lr=1e-3** для CNN baseline, **3e-4** для BiLSTM конфигов (меньше, т.к. LSTM чувствителен к большому LR).
**weight_decay=5e-4** (CNN), **1e-4** (BiLSTM) — регуляризация для предотвращения переобучения.

### 4.4 Scheduler: OneCycleLR vs CosineAnnealingWarmRestarts

**OneCycleLR** (Smith & Topin, 2019): linear warmup → cosine anneal. Использовался во всех конфигах кроме CNN v2.
- Хорошо работает при фиксированном числе эпох
- Одноразовый: после прохождения полного цикла learning rate = ~0, обучение фактически останавливается

**CosineAnnealingWarmRestarts** (Loshchilov & Hutter, 2017): периодические "горячие перезапуски" LR.
- T_0=10: первый цикл = 10 эпох
- T_mult=2: каждый следующий цикл в 2 раза длиннее (10, 20, 40...)
- eta_min=1e-6: минимальный LR

Применён для CNN baseline v2, т.к. при 50 эпохах OneCycleLR "выдыхался" к 30-й эпохе, а warm restarts давали новые шансы на улучшение.

### 4.5 Аугментация данных

#### SpecAugment (Park et al., 2019)

Маскирование случайных полос в спектрограмме:
- **Frequency masking**: до 20 полос (из 128) — учит модель быть робастной к пропуску отдельных частотных компонент
- **Time masking**: до 60 фреймов (v2, было 50 в v1) — учит модель предсказывать по неполному временному контексту

Применяется только при обучении. Стандартная техника для аудио-классификации.

#### Temporal jitter (добавлено в v2)

Случайный сдвиг начала окна на ±1.0 секунду:
```python
if self.training:
    jitter = random.uniform(-1.0, 1.0)
    start_sec = max(0.0, start_sec + jitter)
```

**Обоснование**: границы сегментов в аннотациях Harmonix Set заданы с точностью ~0.5–1.0с. Jitter учит модель быть робастной к неточности boundary alignment. Также увеличивает разнообразие тренировочных примеров (data augmentation effect).

#### Mixup (Zhang et al., 2018)

Линейная интерполяция пар примеров и их меток:
```
x_mix = λ · x_i + (1-λ) · x_j
y_mix = λ · y_i + (1-λ) · y_j
```

α=0.2 (per-window конфиги), α=0.0 (BiLSTM конфиги — mixup нарушает временную когерентность последовательностей).

### 4.6 RoundRobinLoader

Поскольку 3 датасета имеют разные задачи (DEAM → arousal/valence, Harmonix → segment, GTZAN → genre), мы не можем объединить их в один DataLoader. Вместо этого RoundRobinLoader чередует батчи:

```
Batch 1 (DEAM): обновляем backbone + arousal/valence heads
Batch 2 (Harmonix): обновляем backbone + segment head
Batch 3 (GTZAN): обновляем backbone + genre head
Batch 4 (DEAM): ...
```

**Преимущество**: backbone получает градиенты от всех задач каждые 3 батча, что обеспечивает сбалансированное обучение.

## 5. Результаты

### 5.1 Результаты v1 (первый запуск)

**Конфигурация**: 30 эпох, window=8s, OneCycleLR, focal_gamma=2.0, max_class_weight=4.0, 4 conv-блока.

| Config | Segment acc/F1 | Arousal acc/F1 | Valence acc/F1 | Genre acc/F1 |
|--------|---------------|----------------|----------------|--------------|
| CNN per-window | 24.3 / 23.1 | 65.9 / 65.3 | 55.8 / 53.4 | 82.7 / 81.9 |
| CNN+BiLSTM | 25.9 / 26.8 | 53.0 / 51.8 | 49.5 / 48.4 | 45.5 / 42.5 |
| PANNs per-window | 23.2 / 20.5 | 60.9 / 61.4 | 54.3 / 52.7 | 81.6 / 81.2 |
| PANNs+BiLSTM | 31.4 / 31.5 | 62.8 / 62.9 | 55.9 / 56.0 | 81.0 / 80.5 |

### 5.2 Диагностика проблем v1

**Segment classification (24.3%)**:
Per-class анализ выявил критический дефект — модель подавляла мажоритарные классы:

| Класс | Precision | Recall | F1 | Интерпретация |
|-------|-----------|--------|----|---------------|
| Intro | 28.9% | 64.2% | 39.8% | Overpredicted |
| Verse | 68.9% | **10.1%** | 17.6% | Почти не предсказывается! |
| Bridge | 19.2% | 51.5% | 28.0% | Overpredicted |
| Chorus | 70.9% | **18.4%** | 29.2% | Почти не предсказывается! |
| Instrumental | 10.0% | 62.5% | 17.3% | Overpredicted, низкая precision |
| Outro | 4.1% | 14.4% | 6.4% | Плох везде |

**Диагноз**: max_class_weight=4.0 чрезмерно усиливал миноритарные классы. Модель "перестраховывалась", предсказывая Intro/Bridge/Instrumental вместо Verse/Chorus, поскольку ошибка на миноритарном классе стоила в 4 раза дороже.

**CNN+BiLSTM genre (45.5%)**:
Катастрофическое переобучение. Train accuracy достигала >90%, но val accuracy — 45%. Причина: BiLSTM с ~400K параметров обучался на 699 треках (genre), этого недостаточно. Per-window CNN не страдал от этого, т.к. видел ~16K окон.

**Valence neutral (28% recall)**: нейтральный класс плохо разделяется. Граница между Dark и Neutral, Neutral и Bright субъективна. Это известная проблема в MER (Music Emotion Recognition) — средние значения arousal/valence наименее согласованы между аннотаторами.

### 5.3 Результаты v2 (после улучшений)

## 6. Анализ факторов: ответы на исследовательские вопросы

### 6.1 RQ1: Эффективность мульти-задачной CNN

Мульти-задачная CNN (Конфиг 1, v2) показала:
- **Genre: 83.9%** — конкурентный результат, в диапазоне типичных CNN на GTZAN (75–85%)
- **Arousal: 62.0%** — почти в 2 раза лучше рандома (33%), значимый результат
- **Valence: 51.7%** — слабо, нейтральный класс проблематичен
- **Segment: 35.3%** — в 2 раза лучше рандома (17%), но в абсолюте низкая точность

**Ответ**: мульти-задачный подход работоспособен. Одна модель с ~800K параметрами решает 4 задачи одновременно. Genre и arousal — удовлетворительно, segment и valence — требуют дополнительной работы.

### 6.2 RQ2: Вклад temporal modeling (BiLSTM)

Сравнение конфигов с BiLSTM vs без (v2):

| Задача | CNN | CNN+LSTM | Δ (BiLSTM вклад) |
|--------|-----|----------|-------------------|
| Segment | 35.3 | 32.2 | **-3.1** |
| Arousal | 62.0 | 62.3 | +0.3 |
| Valence | 51.7 | 54.2 | **+2.5** |
| Genre | 83.9 | 60.9 | **-23.0** |

| Задача | PANNs | PANNs+LSTM | Δ (BiLSTM вклад) |
|--------|-------|------------|-------------------|
| Segment | 24.0 | 32.9 | **+8.9** |
| Arousal | 61.2 | 64.9 | **+3.7** |
| Valence | 53.8 | 55.0 | +1.2 |
| Genre | 81.9 | 77.7 | **-4.2** |

**Ответ**: BiLSTM вносит **положительный вклад для segment (+8.9 с PANNs)** и **arousal (+3.7)**, но **вредит genre** (-23.0 с CNN, -4.2 с PANNs). Причина деградации genre: BiLSTM обучается на последовательностях целых треков, но для genre все окна трека имеют одну метку — BiLSTM не получает полезного сигнала из temporal context, при этом добавляет параметры и риск переобучения.

Segment — задача, где temporal context наиболее важен (тип сегмента зависит от позиции в треке), и BiLSTM действительно помогает (+8.9 с PANNs). Однако с CNN embeddings BiLSTM ухудшает segment (-3.1) — вероятно, 512-dim CNN embeddings уже содержат достаточно информации для per-window классификации, и BiLSTM добавляет шум.

### 6.3 RQ3: Вклад качества признаков (PANNs vs CNN)

Сравнение PANNs vs CNN при одинаковом temporal modeling (v2):

| Задача | CNN | PANNs | Δ (pretrained вклад) |
|--------|-----|-------|----------------------|
| Segment | 35.3 | 24.0 | **-11.3** |
| Arousal | 62.0 | 61.2 | -0.8 |
| Valence | 51.7 | 53.8 | +2.1 |
| Genre | 83.9 | 81.9 | -2.0 |

| Задача | CNN+LSTM | PANNs+LSTM | Δ (pretrained вклад) |
|--------|----------|------------|----------------------|
| Segment | 32.2 | 32.9 | +0.7 |
| Arousal | 62.3 | 64.9 | **+2.6** |
| Valence | 54.2 | 55.0 | +0.8 |
| Genre | 60.9 | 77.7 | **+16.8** |

**Ответ**: неожиданный результат — **PANNs pretrained embeddings не дали систематического преимущества** перед нашей CNN. В per-window режиме CNN даже значительно лучше PANNs на segment (-11.3) и genre (-2.0). Однако в комбинации с BiLSTM PANNs лучше на genre (+16.8) и arousal (+2.6).

**Объяснение**: PANNs CNN14 предобучен на AudioSet (звуковые события: лай собак, сирены, речь). Музыкальные задачи — не его основная специализация. Наш CNN, обученный end-to-end на музыкальных данных, лучше адаптирован к специфике музыки (гармония, ритм, тембр инструментов). PANNs embeddings "универсальнее", но менее специализированы.

### 6.4 RQ4: Какой фактор важнее?

| Задача | Вклад BiLSTM (avg) | Вклад PANNs (avg) | Что важнее? |
|--------|--------------------|--------------------|-------------|
| Segment | +2.9 | -5.3 | **Ни то, ни другое** (CNN per-window лучший) |
| Arousal | +2.0 | +0.9 | **BiLSTM** (temporal context) |
| Valence | +1.9 | +1.5 | **Примерно равны** |
| Genre | -13.6 | +7.4 | **Features** (но BiLSTM вреден) |

**Ответ на RQ4**: вклад факторов **зависит от задачи**:
- Для **arousal** важнее temporal context (BiLSTM +2.0 vs PANNs +0.9) — энергетика песни меняется в контексте
- Для **genre** важнее quality of features (PANNs +7.4), а temporal context вреден (-13.6) — жанр определяется тембром и ритмом, а не позицией в треке
- Для **segment** и **valence** оба фактора вносят скромный вклад — эти задачи требуют иных подходов (более сильные backbone, больше данных)

## 7. Технические сложности и решения

### 7.1 FFmpeg не найден (yt-dlp)

**Проблема**: 912/912 загрузок Harmonix аудио через yt-dlp провалились. Функция `_find_ffmpeg()` возвращала `None`.

**Причина**: `imageio-ffmpeg` был установлен в conda-окружение, но проект использует `.venv` (pip virtualenv). yt-dlp не мог найти ffmpeg в PATH.

**Решение**: `pip install imageio-ffmpeg` внутри `.venv`. После этого 746 из 912 треков успешно загружены (81.8%), остальные удалены с YouTube.

### 7.2 Агрессивные class weights

**Проблема**: v1 segment accuracy = 24.3%. Per-class анализ показал Verse recall = 10%, Chorus recall = 18%.

**Причина**: `max_class_weight=4.0` делал ошибки на Outro/Instrumental в 4 раза "дороже" ошибок на Verse. Модель минимизировала loss, жертвуя accuracy на мажоритарных классах.

**Решение**: снижение `max_class_weight` до 2.5, снижение `focal_gamma` с 2.0 до 1.5. Результат: Verse recall 10→28%, Chorus recall 18→40%, segment accuracy 24.3→35.3%.

### 7.3 Early stopping выбирал не лучшую модель

**Проблема**: `best.pt` (по val_loss) показывал segment=30.5%, но `last.pt` — segment=35.3%.

**Причина**: val_loss суммирует потери по всем задачам. Модель с лучшим val_loss оптимизировала arousal/valence (лёгкие задачи) за счёт segment (сложная задача). `last.pt` продолжал улучшать segment после того, как суммарный val_loss перестал падать.

**Решение**: использование `last.pt` вместо `best.pt` для CNN v2. В будущем: отслеживать per-task метрики для early stopping, а не суммарный loss.

### 7.4 CNN embeddings: размерность 256 → 512

**Проблема**: после апгрейда backbone с 4 до 5 блоков размерность GAP output изменилась с 256 на 512. Precomputed embeddings остались 256-dim, т.к. скрипт проверял `if out_path.exists(): continue`.

**Решение**: удаление старых `.npy` файлов + повторный precompute. Обновление `embedding_dim` в конфигах BiLSTM и `projection_dim` в PANNs.

## 8. Выводы и перспективы

### 8.1 Что достигнуто

1. **Работающий multi-task pipeline**: одна модель (~800K параметров) решает 4 задачи анализа музыки одновременно. End-to-end: от аудиофайла до timeline с сегментами, эмоциями и жанром.

2. **Genre classification 83.9%** — конкурентный результат на GTZAN бенчмарке (литературный диапазон для CNN: 75–85%).

3. **2×2 факторный эксперимент** с чёткими выводами: temporal context помогает arousal, pretrained features помогают genre, но ни один фактор не является универсальным решением.

4. **Документированный путь улучшений**: segment accuracy вырос с 24.3% до 35.3% (+45% относительно) через систематическую диагностику и 5 направлений оптимизации.

5. **AST (Audio Spectrogram Transformer)**: дополнительный эксперимент с pretrained transformer backbone (MIT/ast-finetuned-audioset, 85M params). AST достиг **segment 40.3%** — лучший результат проекта (+5.0% над CNN v2), подтверждая гипотезу о преимуществе pretrained transformer representations для структурной сегментации.

### 8.1.1 Эксперимент с AST

Для проверки гипотезы о влиянии мощности backbone был добавлен 5-й конфиг: **Audio Spectrogram Transformer** (AST), pretrained на AudioSet (2M аудиозаписей, 527 классов). Архитектура: 12-слойный Vision Transformer с patch size 16×16 на log-mel спектрограммах.

**Конфигурация**: freeze первых 10 из 12 слоёв (fine-tune только 2 верхних + classification heads), differential learning rate (backbone 5e-5, heads 1e-3), dropout 0.3, weight_decay 0.01.

**Оптимизация скорости**: hop_seconds увеличен с 1.0 до 5.0 (в 5 раз меньше training samples), что сократило обучение с ~24 часов до ~2 часов. Обучение: 8 эпох (early stopping, patience=4).

**Результаты AST (test set)**:

| Checkpoint | Segment acc/F1 | Arousal acc/F1 | Valence acc/F1 | Genre acc/F1 |
|------------|---------------|----------------|----------------|--------------|
| AST last.pt | **40.3/31.5** | 61.9/61.9 | 48.8/49.0 | 81.1/79.7 |
| AST best.pt | 33.0/28.2 | 59.9/60.0 | 51.6/51.9 | 81.3/80.4 |

**Анализ**: AST показал лучший результат по segment (+5.0%), но не улучшил остальные задачи. Причины:
- **Переобучение**: train accuracy достигала 96–100%, а val стагнировала (~60%). С hop=5.0 train set уменьшился в 5 раз — pretrained модель недополучала данные.
- **Frozen layers**: 10 из 12 слоёв заморожены — модель не могла адаптировать нижние представления под музыкальные задачи.
- **Отсутствие mixup**: для transformer augmentation особенно важна, но mixup не применялся.

Направления улучшения AST: (1) вернуть hop=1.0 с gradient accumulation, (2) разморозить больше слоёв с меньшим LR, (3) добавить SpecAugment + CutMix.

### 8.2 Ограничения

1. **Segment accuracy 40.3%** (AST) / 35.3% (CNN) — хотя это 2.4× random baseline (17%), для production-системы недостаточно. Основная причина: 6-классовая сегментация с сильным дисбалансом на малом датасете (746 треков).

2. **Valence ~55%** — нейтральный класс плохо разделяется. Это известная проблема в MER, связанная с субъективностью аннотаций.

3. **BiLSTM overfitting на genre** — при малом числе треков (699 GTZAN) BiLSTM добавляет параметры без пользы.

4. **PANNs без ожидаемого преимущества** — AudioSet pretrained embeddings не оптимальны для музыкальных задач.

### 8.3 Направления дальнейшего улучшения

1. **Audio Spectrogram Transformer (AST)**: замена CNN backbone на AST/HTS-AT, pretrained на AudioSet. Ожидаемый прирост: genre 84→93%, arousal 64→75%, segment 35→50%. Трансформерная архитектура с self-attention лучше захватывает глобальные паттерны в спектрограмме.

2. **Boundary detection для сегментации**: вместо классификации каждого окна независимо, обнаруживать границы между сегментами (change-point detection). Литература показывает, что boundary F1 значительно лучше correlates с perceptual quality.

3. **Regression вместо classification для emotion**: arousal/valence — непрерывные величины. Квантизация в 3 класса теряет информацию. Регрессия с MSE/CCC loss и последующей визуализацией на circumplex model.

4. **Ensemble**: усреднение предсказаний нескольких конфигов. Бесплатный прирост 2–3% без дополнительного обучения.

5. **Увеличение данных**: MusicNet, FMA, MTG-Jamendo — дополнительные датасеты для emotion и genre.
